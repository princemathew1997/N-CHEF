# D1 migration status

Account: N-CHEF admin (`admin.nchef@gmail.com`).
Database: `nchef-db`; binding: `DB`; location hint: APAC.
The checked-in Wrangler configuration contains public resource identifiers, not credentials.

## Phase 1: fresh database

Versioned migrations create relational tables and seed 5 outlets, 4 vendors,
6 cuisines, and 10 catalog items from the current project. All opening stock
is zero. Demo passwords, users, requests, indents, and purchase orders are
excluded. The existing catalog includes an item named `sample`; review that
catalog before operational use.

`0002_fresh_catalog.sql` is generated by `node scripts/generate-catalog-seed.mjs`.
After applying a migration, make subsequent catalog changes in a new migration
or through the future API; do not regenerate an already applied migration.

Commands from the project directory (Node/npm must be on PATH):

```powershell
python -m unittest discover -s tests -v
npx wrangler d1 migrations apply DB --local
npx wrangler d1 migrations apply DB --remote
npx wrangler d1 migrations list DB --remote
npx wrangler d1 export DB --remote --output ./backups/nchef-db.sql
```

Remote commands write to the actual database. Local commands use the separate
development database under `.wrangler`, never the remote database.
SQL backups contain business data and must stay outside version control.

## Phase 2: authenticated API and interface

The website now uses `js/api-data.js`; it does not read or seed business data
from localStorage. View preferences remain local. `js/data.js` is the old demo
source used by the catalog generator and is excluded from deployments.

The private `nchef-api` Worker is accessed through the Pages `API` service
binding. Pages serves the interface and forwards `/api/*` on the same origin.
There is no public workers.dev endpoint or wildcard CORS. Worker logs and
sampled traces are enabled. Local development combines assets and the API.

### Authentication

- First-admin setup requires the random `SETUP_TOKEN` Worker secret. A database
  uniqueness guard allows setup only once, even if two requests race.
- Passwords must be 12–128 characters. They are salted and hashed using
  PBKDF2-SHA256 with 100,000 iterations (supported by Workers Web Crypto).
  Plaintext passwords are never stored in D1 or returned in API responses.
- Sessions expire after 8 hours. HTTPS cookies use `__Host-`, `Secure`,
  `HttpOnly`, and `SameSite=Strict`. Session tokens are stored only as hashes.
- Logout and account changes revoke sessions. Login attempts are throttled
  per username and IP. Mutation requests require matching Origin and JSON.
- API permissions come from the database, not UI visibility. Supervisors can
  manage chefs within their assigned outlets. Chefs can create requests only
  for their assigned outlets/cuisines and edit their own unforwarded requests.

### Data and transactions

The compatibility endpoint accepts a list of changed records, not a complete
browser snapshot. Each command includes an operation UUID and expected global
revision. A foreign-key revision guard, business writes, ledger entries, audit,
and revision advance run in one atomic D1 batch. Concurrent stale saves return
409 instead of overwriting work. Exact command retries return the committed
state. Failed saves restore confirmed data and display an error.

State refresh runs every 10 seconds while the page is visible and the user is
not editing. This is polling, not WebSocket realtime. Administrators see all
data; outlet users receive scoped requests, users, indents, and stock values.
The global revision favors correctness for a small team: unrelated simultaneous
edits can also conflict and must be retried. Up to 150 changed records are
accepted per command.

The relational tables enforce foreign keys and quantity checks. JSON payload
columns preserve existing UI metadata while normalized balances, request links,
order lines, permissions, and ledger entries remain queryable with SQL.
Removed records are deactivated for history. Referenced catalog entries cannot
be removed while still in use; items with stock history cannot be deleted.

Explicit server actions handle central receipts, outlet consumption, full
purchase-order receiving, and individual/bulk approvals. Central stock must
exist before approval. Receiving a purchase order adds its remaining quantity
directly to the destination outlet and can happen only once. Partial deliveries
are not currently exposed. A dispatch workflow separate from approval retains
the existing app behavior; approval allocates stock directly to the outlet.

Because the existing interface uses HTML template strings, API text validation
currently rejects markup, quotes, and backslashes in business display fields.
Passwords are not subject to that display-field restriction.

### Endpoints

| Endpoint | Purpose |
| --- | --- |
| GET `/api/setup-status` | Whether the first admin is required |
| POST `/api/setup` | Create first admin with the setup key |
| POST `/api/login`, POST `/api/logout`, GET `/api/session` | Server sessions |
| GET `/api/state` | Scoped, confirmed state |
| POST `/api/changes` | Validated record changes |
| POST `/api/stock/receipt` | Admin central receiving |
| POST `/api/stock/consume` | Consumption within assigned outlets |
| POST `/api/purchase-orders/receive` | Admin/supervisor full PO receiving |
| POST `/api/indents/approve`, POST `/api/indents/approve-all` | Atomic approvals |
| POST `/api/requests/approve` | Individual unlinked request allocation |
| GET `/api/health` | Database connectivity |

### Run, test, deploy

```powershell
npm ci
npm run db:local
node scripts/setup-key.mjs
npm start
npm test
npm run test:database
```

Local `npm start` uses a separate D1 database on localhost:8000. Open
`/setup.html` and use the key from ignored `.dev.vars` to create the local admin.
Local and production accounts/data are separate.

Deployment order:

```powershell
npm run build
npm run db:remote
npx wrangler deploy
node scripts/setup-key.mjs --upload
npm run deploy:pages
```

The setup key is sent through stdin, never a command-line argument or Git file.
After first-admin setup, remove the secret with `npx wrangler secret delete
SETUP_TOKEN` (this deploys a new version). The database setup lock already
prevents further account creation via setup.

Only allowlisted site assets are uploaded. Do not serve the entire repository
with a generic HTTP server; it contains development tools and ignored secrets.
Never ship the disposable QA app or its test credentials. Production starts
with no accounts until an owner completes setup; do not add demo users.

GitHub ownership transfer and Wix domain connection remain separate tasks.
